The problem

Anomalies hide in plain sight.

A finance team's CSV statement is just rows. A €8,200 cloud overrun and a €12 duplicate look the same in a spreadsheet — until the bill arrives.

Today

Manual review

Someone scans 200 rows on the 3rd of the month, eyeballs the totals, misses the duplicate Stripe charge from the 14th.

When it scales

It doesn't.

Past a few hundred rows, eyeballing fails. Anomalies move from "small mistake" to "5–15% of cloud spend" — quietly, every month.

When discovered

Weeks later.

The vendor bill arrives, accounting reconciles it, the spike becomes obvious. The window to dispute or kill the subscription is already closed.

Why existing tools don't fix this

Detection is the gap.

Bank dashboards

Show, don't flag.

Built to display transactions, not to compare them against history. No notion of "unusual."

Accounting software

Categorize, don't detect.

Xero, QuickBooks, Pennylane label transactions and roll them up. They report what happened, not whether it was strange.

Custom ML

Needs years of data.

Anomaly-detection models want multi-year, multi-account training data. And "the model decided" isn't an answer the CFO will accept.

Generic LLM

Unauditable, unreliable.

"Ask ChatGPT to find anomalies" is non-deterministic. Two runs, two answers. Nothing to point at when defending the call.

The solution

Drop a CSV. Get the alert.

  • Drive trigger. Watched folder fires within 60s of upload.
  • Four deterministic rules. Spike, new vendor, duplicate, category total. All grounded in financial logic, all explainable in numbers.
  • AI for language only. Claude names vendors and writes alert reasons. Math stays in code.
  • Real-time Slack alerts. Severity-coded, with the actual ratio quoted.
  • Replayable by design. Same file twice ⇒ same one set of rows.

Detection logic

Four rules. Every flag has a number.

Rule 1 · High

Amount spike vs vendor history

New charge fires both: amount > 2 × mean and amount > mean + 2σ, computed over the vendor's last 90 days. Skips vendors with fewer than 3 prior samples.

e.g. AWS €8,200 → "2.9× the 90-day average (€2,820, σ=€85, n=3)"

Rule 2 · Low

New vendor

Vendor name never seen in history. Informational, not alarming — most new vendors are legitimate purchases. A soft signal that warrants a glance, not a page.

e.g. Linear App Inc → "First time seeing vendor 'Linear'"

Rule 3 · Medium

Duplicate

Same vendor + same amount within 48 hours, against history or another row in the same incoming batch. Catches billing retries and accidental re-charges.

e.g. 2× Stripe Fee €2.50 on 2026-05-02

Rule 4 · High

Category total spike

Current-month total per category > 2.5× trailing 6-month average. Flags only the largest contributing transaction — one alert per spike, not N noisy alerts.

e.g. Marketing €4,500 → "5.7× the 6-month average (€795)"

The key design decision

Math is in JavaScript.
Words are in Claude.

They don't trade jobs. The detection layer is auditable code; the language layer is generative AI; neither pretends to be the other.

Detection

Deterministic rules

Pure JavaScript. Same input ⇒ same output, every time. Reviewable, testable, defensible. The rules are the model.

Categorization

Claude Haiku 4.5

Cheap, fast, batched. Cleans vendor names and assigns categories. Non-blocking — wrong category degrades the report, not the detection.

Explanation

Claude Sonnet 4.6

One call per flagged transaction, given the rule context. Translates a ratio and a statistical baseline into a sentence a human reads in 5 seconds.

If a reviewer asks "why was this flagged?", the answer is a number — not a model output.

Rules can stack

Real anomalies often trip multiple rules. AWS at €8,200 is both a vendor-level spike and a category-level spike. Linear is both a new vendor and a category spike contributor. The rules are independent and additive — no rule masks another.

Severity is preserved

Each flag carries its own severity. The Slack alert is color-coded by the highest severity in the stack. High Medium Low

Validated before deployment

The rule engine runs against synthetic data before any Slack credential is wired — fast feedback loop, zero infrastructure required.

Production-grade by design

Replay-safe, by construction.

Drive triggers are not exactly-once. Re-runs, restarts, manual re-uploads — without protection, every duplicate event creates duplicate Sheet rows and false anomalies. The fix is one line of design discipline.

Transaction ID — built at parse time, never changes

Before any other processing, the dedup step reads existing IDs from the Sheet and silently drops any row whose ID is already present.

What this buys

  • Re-uploadable. Same CSV ten times ⇒ one set of rows.
  • Replayable on failure. If the AI step fails halfway, the partial run is safe to retry — only genuinely-new rows make it through.
  • No state to maintain. The "have I seen this before?" answer lives in the Sheet, not in some sidecar database.
  • Trivially debuggable. Every transaction has a stable, human-readable identifier you can grep for.

Infra cost

n8n self-hosted, Google Sheets/Drive/Slack on free tiers. The LLM call is the only variable cost.

Two design decisions hold the number

1. Batched categorization. 50 transactions in a single prompt. A 200-row file is 4 calls, not 200 — same quality, two orders of magnitude cheaper.

2. Gated explanation. Sonnet runs only on flagged transactions. Clean day, zero anomalies, zero Sonnet calls. The expensive model sits behind cheap logic.

Honest scope

What it doesn't do — and what's next.

Current limitations

  • One CSV format. Three columns: date, description, amount. Real banks vary.
  • No PDF parsing. Most banks export PDFs; that's a project of its own.
  • Single currency. No FX conversion or per-account currency.
  • Sheets as DB. Comfortable to ~10k rows; needs SQLite past that.
  • Hand-tuned thresholds. 2× mean / 90 days / 2.5× monthly are defaults, not learned.
  • Single user. No multi-tenancy, no auth.

Roadmap

  • Multi-bank format adapter. Header-signature detection, then remap to the canonical shape.
  • Confidence-weighted score. Combine the four rules into a single 0–1 score per transaction; sort the daily digest by it.
  • Per-vendor charts in Slack. 6-month sparkline embedded in the alert. Makes it verifiable in one glance.
  • SQLite backing store. Keep Sheets for the human view, move queries to a real DB.
  • Per-vendor thresholds. Spiky vendors (cloud) need different defaults than flat ones (SaaS).
  • Weekly executive summary. Sunday Cron → Sonnet → 5-bullet email.
What this demonstrates

Five things, intentionally.

  • Hybrid AI/code architecture. The LLM sits behind deterministic logic — either layer can be swapped without touching the other.
  • Idempotent event processing. Drive triggers aren't exactly-once. A deterministic transaction ID + dedup-on-read makes the pipeline replayable.
  • Cost-aware API usage. Batched categorization, gated explanation. Two orders of magnitude vs the naive version.
  • Schema-first design. The Sheet's columns were settled before any node was built. Easy to underestimate; expensive to retrofit.
  • Scope discipline. Multi-bank, PDF, multi-currency, custom UI — all explicitly out. The project is recruitable because it does one thing end-to-end.
